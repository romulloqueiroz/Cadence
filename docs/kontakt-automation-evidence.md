# Kontakt host-automation reference

Read on 2026-11-06 to guide Cadence's independent rack-to-DAW automation design.

## Source and limits

This is a focused reading of the saved REA/Ghidra export of **Kontakt 8.14.1's ARM64 main executable** in `../../Kontakt-8-REA/`. The target SHA-256 recorded and previously rechecked in this investigation is `42a3216b527e8eaaa2b53122acb9f11cdc1db5fbe9b7571777f362b5cc8d4ec3`; see the archive [README](../../Kontakt-8-REA/README.md). Reviewed files report Ghidra 12.1.4 and analysis profile `040072c9c8ab8c896677a5e18badb276196ce107557bde41bc438752d586aebd`.

The [unified function catalog](../../Kontakt-8-REA/combined-functions.tsv) was searched for core `BEngine`, `BProgramContainer`, `BAutomationObject`, `BProgram`, `BInstrument`, and host-interface automation functions. This pass used saved artifacts only: no binary import, new REA session, Kontakt execution, or runtime counter/memory mutation. The addresses identify static saved observations, not newly issued REA Evidence IDs. Pseudocode is not original source, and signatures/parameter locations can be imperfect, especially for floating-point/virtual-call arguments. The limitations in each linked artifact remain applicable.

## Findings and design implications

| Question / saved function | Observed static behavior | Implication for Cadence |
| --- | --- | --- |
| Host control versus internal target: [`BEngine::ReceiveHostAutomation`, `0x1003ea48c`](../../Kontakt-8-REA/pseudocode/functions/0x1003ea48c.c), and [`BProgramContainer::ReceiveHostAutomation`, `0x1003ea530`](../../Kontakt-8-REA/pseudocode/functions/0x1003ea530.c) | The engine accepts an inbound ID below `0x800` while an inhibition field permits it, marks an ID-indexed bit, and visits 64 program containers. A container accesses an assignment list selected by that host ID; it walks the list and calls `BAutomationObject::SetFromExternal`, optionally filtering by the selected program. It uses `recursive_mutex::try_lock`; a failed lock returns without dispatch in this visible path. | A stable host control can be separate from its current internal assignment. The original lists can fan one ID out to several targets; Cadence's eight controls and one-target-per-control policy are independent choices. Publish resolved routes safely; do not copy a lock-dependent dropped-update path into Cadence's realtime bridge. |
| Creating and deduplicating mappings: [`BEngine::NewAutomationObject`, `0x100392b84`](../../Kontakt-8-REA/pseudocode/functions/0x100392b84.c) | Searches existing objects for a tuple including host address mode/ID and target selectors/parameter tag. When absent, it builds replacement assignment storage, associates the runtime engine, and exchanges storage directly under allowed conditions or through a synchronized threading job. It then calls `UpdateAutomationEngine`. With its final option enabled, it reads the target's current value and calls `SetAutomationSoftValue` with action `4`. | Make assignment identity explicit and avoid duplicates. Resolve target handles outside audio processing, then publish a complete mapping. Initializing a newly assigned host control from the target's current value is consistent with this reference; the exact host-notification policy remains Cadence's decision. |
| Rebuilding routes: [`BEngine::UpdateAutomationEngine`, `0x1003924f4`](../../Kontakt-8-REA/pseudocode/functions/0x1003924f4.c) | Locks a program container, clears routing lists, and relinks automation objects into lists selected by address mode and numeric ID. Objects with host mode `2` are linked into the host-ID table. | Persistent assignment metadata and the live dispatch table are different representations. Rebuild/resolve after loading, removing, or replacing a target; never let a saved transient pointer become a live route. |
| Persistent target description: [`BAutomationObject::doWrite`, `0x1007b1df8`](../../Kontakt-8-REA/pseudocode/functions/0x1007b1df8.c), [`doRead`, `0x1007b1ec0`](../../Kontakt-8-REA/pseudocode/functions/0x1007b1ec0.c), and [`postRead`, `0x1007b217c`](../../Kontakt-8-REA/pseudocode/functions/0x1007b217c.c) | Write stores the address-mode field, a flag, a 16-bit ID, two target-selector integers, two range endpoints, and a parameter tag converted to a string. Read recognizes versions `0x70` / `0x71`, rejects unsupported mode values/versions, and converts the string back to a tag. `postRead` attaches runtime target/engine context from the read context and derives a parameter behavior field. No runtime engine pointer is written by the reviewed writer. | Save stable host-control IDs separately from the target's persistent identity and parameter key; resolve runtime pointers after state load. Cadence's slot UUID plus parameter key is its own scheme, not a recovered Kontakt UUID format. Version and validate the XML mapping schema, including unresolved/missing targets. |
| Equality: [`BAutomationObject::IsEqual`, `0x1003919e0`](../../Kontakt-8-REA/pseudocode/functions/0x1003919e0.c) | Compares mode/flag/ID, parameter tag, target selector fields, and range endpoints. The compared persistent description is richer than a display label. | Target display names and current list positions are insufficient identity. Preserve keys through rack reorder and reject ambiguous replacements. |
| Removing assignments: [`BEngine::RemoveAutomationObject`, `0x10039403c`](../../Kontakt-8-REA/pseudocode/functions/0x10039403c.c) | Matches a combination of target selectors, tag, address mode, and host ID, constructs replacement storage omitting the selected object, exchanges it through the same synchronized pattern, then updates routing. | Unassigning/removing a target must remove the live route before the target disappears. A missing mapping should remain inert, rather than falling through to a new object that happens to occupy the same position. The reference does not prescribe Cadence's UI choice to retain or clear an unresolved saved assignment. |
| Adapting positional targets: [`BEngine::ChExOrd_AdaptAutomation`, `0x10040bfd0`](../../Kontakt-8-REA/pseudocode/functions/0x10040bfd0.c), and [`BProgram::PurgeInvalidAutomationObjects`, `0x100433fa0`](../../Kontakt-8-REA/pseudocode/functions/0x100433fa0.c) | The adaptation function rewrites matching target-selector indices when an object's order changes. Purging deletes zero/invalid tags and assignments whose referenced object/type no longer matches; some other selector fields are normalized. | Stable UUIDs let Cadence preserve target identity across reorder without index arithmetic. Removal/replacement and invalid keys still need explicit handling and tests. This is not evidence that Kontakt's own target identity is UUID-based. |
| Shifting exposed IDs: [`BProgram::shiftUserAutomation`, `0x100432cc8`](../../Kontakt-8-REA/pseudocode/functions/0x100432cc8.c) | Applies a program offset delta to mode-`2` IDs in program/group assignment arrays when a flag permits it, clamping to the range `0..0x800`. | Kontakt has explicit ID-remapping machinery. Cadence can avoid changing DAW-visible control identities by keeping its eight exposed host IDs fixed while changing only their assignments. Its exact ID count and naming/version policy are independent product choices. |
| Incoming normalized values: [`BAutomationObject::SetFromExternal`, `0x10031f8c0`](../../Kontakt-8-REA/pseudocode/functions/0x10031f8c0.c) | The continuous branch computes `range_start + (range_end - range_start) * incoming`, records an external-touch timestamp, optionally runs pickup/crossing logic using a small threshold, then calls `IO_SetEnginePar`. Another branch treats a value above `0.5` as a boolean. | Keep host-normalized values distinct from target-native values and use the target parameter's conversion/stepping rules. Cadence should clamp/reject nonfinite values itself; this reviewed continuous branch alone does not establish a universal input-validation contract. Pickup behavior is optional and not necessary to reproduce for this task. |
| Target-to-host values: [`BEngine::SetAutomationSoftValue`, `0x100393284`](../../Kontakt-8-REA/pseudocode/functions/0x100393284.c) | Matches target selectors/tag against host assignments, computes a normalized value from range endpoints (or a boolean path), clamps the visible outgoing value to `0..1`, updates cached fields, and invokes the host-send callback with ID, value, action, and thread classification. The visible loop suppresses repeated callback invocation after the first matching host assignment it sends. | Bidirectional synchronization must normalize values consistently and distinguish host-originated updates from user gestures to avoid notification loops. Cadence's policy for multiple controls assigned to one target needs its own tests; this partial outbound path is not a full fanout specification. |
| Gesture dispatch: [`BInstrument::SendHostAutomation`, `0x1007e7548`](../../Kontakt-8-REA/pseudocode/functions/0x1007e7548.c) | Checks the exposed parameter count, calls `touchAutomationParameter` for action `1` or `4`, calls `changeAutomationParameter`, then calls `releaseAutomationParameter` for action `3` or `4`. | Bracket user drags with begin/change/end notifications; an isolated complete edit can emit all three. The enum names were not recovered, so these are observed numeric branches, not asserted source-level enum names. Ensure unassign/close/cancel ends any active gesture and tests distinguish host replay from UI writeback. |

The host-interface calls themselves are thin virtual dispatches at [`IInstrument::touchAutomationParameter`, `0x101ea7458`](../../Kontakt-8-REA/pseudocode/functions/0x101ea7458.c), [`changeAutomationParameter`, `0x101ea7468`](../../Kontakt-8-REA/pseudocode/functions/0x101ea7468.c), and [`releaseAutomationParameter`, `0x101ea7478`](../../Kontakt-8-REA/pseudocode/functions/0x101ea7478.c). The saved provider warns that their indirect jumps could not be recovered as jump tables. Concrete AU/VST host behavior beyond those calls was not traced here.

## Timing and unresolved behavior

- The reviewed inbound/outbound automation functions expose IDs and scalar values, with an action/thread classification on the outbound path. They do not establish a sample-offset automation contract. The external-touch timestamp is a system-clock call, not evidence of audio-sample scheduling.
- Exact DAW playback granularity, interpolation/smoothing, gesture callback thread guarantees, host-recording behavior, and automation during pending instrument loading require Cadence tests. No sample-accurate Kontakt parity is claimed.
- `ReceiveHostAutomation` can return while inhibited or when its container lock is unavailable. This focused static trace does not establish whether another path retries/coalesces such updates. Cadence should explicitly define latest-value behavior during loading/remapping rather than infer it from this branch.
- The complete enum meanings, target-selector taxonomy, saved flag meanings, all script-generated target rules, duplicate-assignment fanout, and feedback-loop suppression across every call path remain partially untraced.
- The persistent writer/tag string is observed; a universal guarantee that all third-party/native parameter identifiers remain stable across plugin upgrades is not established. Cadence must bind to a documented target key, preserve unresolved bindings safely, and verify recall/reorder/removal independently.
- Assignment creation/removal visibly allocates and can schedule-and-wait. These are control-thread operations. Realtime value forwarding should use previously resolved routes and bounded storage, without allocation or waiting.

## Cadence validation targets

The resulting design can use eight fixed DAW parameter IDs, each optionally bound to a persisted slot UUID and target parameter key. This is Cadence's independent design, informed by the observed separation of exposed IDs, assignment records, runtime routes, and gesture/value dispatch. Tests should cover assignment initial value, normalized/stepped conversion, automation playback, UI gesture recording, recall with pending loads, slot reorder, target removal/replacement, invalid keys, unassigning during a gesture, and feedback-loop prevention. Any block-level timing limit should be stated directly.
